# Cleaning notes (stage 2)

Generated by `src/02_clean.py`. All numbers come from the run that wrote this file. Datasets A (with firewall) and B (without firewall) are cleaned separately with identical rules. The raw CSVs are never modified.

## Rules, in order

1. **Drop port columns** (Source Port, Destination Port; applied: True). `Source Port` is 8888 in 99.13% (A) and 97.64% (B) of the lab rows and in no external row, so it separates lab rows from external rows without describing any attack behaviour (measurements in `decisions.md`, decision 1). `Destination Port` in the lab rows is the client's ephemeral port. Done first so that the duplicate rules see the same columns the models will see.
2. **Drop rows with NaN or Inf.** `Flow Bytess` and `Flow Packetss` are rates; they are undefined when `Flow Duration` is 0. Inf is converted to NaN and the row is dropped. No row of sqli, Infiltration, dos_slowhttptest is affected (the script stops if one is).
3. **Drop exact duplicates, keep the first.** Identical rows add no information and could land on both sides of a random train/test split.
4. **Drop conflict groups.** Rows with identical features and different labels are removed entirely (all copies), because their label is ambiguous.

Not done on purpose: constant columns are kept (the Low Variance filter in stage 4 removes them), nothing is scaled (scalers are fitted on training rows only), and the 12 labels are kept as they are.

## Why so many duplicates appear

With the port columns present, the raw files contain only 94 (A) and 100 (B) exact duplicate rows (see `results/audit/`). Once the ports are dropped, many rows that differed only in a port number become identical, which is why rule 3 removes far more rows than the audit reported. This is expected and is the reason ports are dropped before deduplication: those rows are indistinguishable to any model trained without ports.

## Limitations

- **One-direction flows.** In 100% of the lab rows the backward packet count is 0 and the flow source is the server (172.16.30.10). The client side of every conversation is missing: no attacker requests and no SQL payloads are represented. NTLFlowLyzer extracts bidirectional flows from the same PCAP, which points to a failure of the flow extraction and not of the capture. That comparison was verified on a single PCAP (`fw_benign_20260828_01`), not on the 12 lab captures; for the other 11 it is assumed, not checked. Cleaning cannot repair this; all `Bwd` features carry no information for lab rows.
- **Two sources mixed.** External rows (IDS2025) and lab rows come from different extractors and use different label vocabularies. Features may separate the data source instead of the attack.
- **Small classes after deduplication.** See the tables above; classes with few remaining rows give unstable per-class metrics.
- **Near duplicates remain.** Only exact duplicates are removed. Rows that differ in a single timing value are kept and may still fall on both sides of the train/test split.
